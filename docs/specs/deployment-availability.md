# Deployment availability

**Proposed 23 November 2026 · Progress updated 25 November 2026.** Keep the web app, REST API, and MCP usable during routine hosted releases. For changes that require a pause, delay background work first, keep compatible reads available, and block writes only as long as correctness requires. Breaking migrations can still ship through full maintenance.

All four tasks have shipped an initial implementation. Production has completed a fast writer drain and a restricted index migration. The online table path passed hosted staging rehearsals and awaits its first qualifying production migration. The task sections retain the original acceptance criteria.

## Task 1 — Drain background work while the app is serving

**Shipped and observed in production.** During the one-time writer enrollment, about 10 minutes elapsed between stopping background workers and cutting over the public routes. The first to last observed REST read 503 spanned 9 min 14 sec. The earlier 17–19 minute intervals are from different releases and Gateway logs, so they provide a baseline comparison. The same production run published phase timings, edge probes, and a routine canary result. [Cloud #35](https://github.com/Tamloot-cc/retainer-cloud/pull/35) · [Production enrollment](https://github.com/Tamloot-cc/retainer-cloud/actions/runs/45324754426)

On 24 November, matched AWS staging releases applied equivalent independent-table migrations through the timed fallback with the same 900-second executor and 300-second control timeouts. The baseline switched the edge immediately after pausing workers. The second release kept the edge open for 600 seconds. Intervals are first-to-last failed first attempts, sampled every two seconds when coverage was available.

| Edge probe | Immediate maintenance | Background-first | Reduction |
| --- | ---: | ---: | ---: |
| REST reads | 18 min 26 sec | 8 min 52 sec | 9 min 34 sec |
| MCP reads | 18 min 22 sec | 8 min 52 sec | 9 min 30 sec |
| Writes | 18 min 26 sec | 8 min 48 sec | 9 min 38 sec |

The background-first routine canary was accepted while workers were paused and succeeded 19 min 38 sec later. Its oldest observed queued age was 19 min 34 sec. In the immediate-maintenance run, another canary was accepted 2 seconds after workers stopped, reached running status, and succeeded 4 seconds after acceptance. CloudWatch shows one executor invocation spanning that interval, starting before workers stopped and finishing after the canary succeeded. This confirms a late routine-job claim by an in-flight executor. Three background-first write read-backs received 503s while the routes transitioned. These read-back samples could not establish the corresponding write outcomes at the time. The staging run had no signed-in browser probe.

A separate hosted staging rehearsal paused executor capacity for 33 seconds. Six validation jobs were accepted and observed queued while the foreground record read still passed. All six jobs succeeded within 23 seconds of restoring the original capacity. Validating the same source again returned the existing successful job.

**Deliverable.** Change the stopped path in the cloud deployer, including its Terraform preparation path. After candidate and maintenance preflight, stop new executor, change, file, and consolidator invocations. Keep API, control, and extension routes live on the old build. Existing executions can finish and callbacks can arrive. Ordinary edits and durably queued work can still be accepted. An operation requiring immediate executor service must either complete within its deadline or return an explicit temporary response before accepting it. Account for queue capacity, expiring tool calls, scheduled ticks and cleanup deadlines.

Overlap the fixed waits. Record the stop time and live timeout of each writer after its stop is confirmed. With the current configuration, keep HTTP open for roughly the first 600 seconds of the executor's 901-second drain. Then route HTTP to maintenance, confirm propagation, stop HTTP writers and wait until the **latest individual deadline**. Preserve the consolidator lock, post-drain lease and release inventory checks, and the existing verification before reopening. This first change can save about ten minutes even on a quiet system with no way to detect idle writers.

Persist background-drain progress separately from the completed full-drain marker. Recovery must distinguish intentionally paused workers from a failed full stop. Bind progress to the deployment and writer identities. If a writer restarted, its identity or timeout changed, or elapsed time cannot be established safely, start a fresh wait for that writer. New resources introduced during apply start closed. Invalidate completed drain proof before restarting the first writer.

**Acceptance.** Extend the cloud AWS simulator's failure-at-each-boundary tests through early stop, route cutover, interrupted prepare/apply, lease recheck and restore. In staging, replay the same short migration and timeouts with and without the change. Target approximately ten fewer minutes of unavailable foreground reads and writes (roughly 7–9 minutes remaining on the observed baseline). Exercise a late job claim, an admitted webhook and a queued job across restart. Verify durable outcomes, retry semantics and backlog catch-up. Record worker delay separately from user-facing downtime.

For all four tasks, probe through the public edge every two seconds from before cutover until recovery. Use a synthetic workspace, an authenticated record read, an idempotent write with read-back, and an MCP read. Record first-attempt responses and latency before client retries. Time a canary job from acceptance to completion and record its oldest queued age. Publish the release IDs, stop reason, phase timestamps, failure windows and probe coverage in the deployment summary. Treat gaps as unknown.

## Task 2 — End the drain when the last unsafe writer has finished

**Shipped and active in production.** PostgreSQL writer admission fences retired builds and can end the drain once admitted transactions and conflicting work have settled. The first production enrollment used the timed path. Staging cleared the writer drain **2.3 seconds** after admission closed, meeting the under-10-second target for that phase. The timed fallback remains available. [Retainer #171](https://github.com/Tamloot-cc/Retainer/pull/171) · [Cloud #36](https://github.com/Tamloot-cc/retainer-cloud/pull/36) · [Staging evidence](https://github.com/Tamloot-cc/Retainer/pull/179)

The production index release reached migration permission **3.47 seconds** after closing admission and recorded 79 ms for applying the journal. It took the fast drain. After recovery, the journal was current and writer admission was open with the candidate as its sole admitted build and zero uncertain effects. A real-Postgres test held an admitted webhook across a failed close attempt, replayed its receipt, and verified that only one candidate execution completed after reopening. [Production release](https://github.com/Tamloot-cc/retainer-cloud/actions/runs/45447065582) · [Webhook test](https://github.com/Tamloot-cc/Retainer/pull/187)

**Deliverable.** Add a versioned writer-admission protocol to Retainer and consume it from the cloud deployer. Its safety invariant is that after drain completion, an old invocation cannot commit another mutation, including after pool reconnect, retry, or reopening for the new build. A lock held by a separate connection today can disappear while a worker's data pool continues. Current release inventory counts extension-job leases only. Neither signal alone establishes that invariant. [Pass and migration locks](../../packages/server/src/lambda/deploy-lock.ts) · [Executor claim and drain loop](../../packages/server/src/lambda/executor.ts)

Use a durable deployment generation and enforce admission on the connection and in the transaction performing each mutation. One design uses a shared transaction lock followed by a check of the permitted generation, paired with an exclusive transition that closes admission and waits for admitted transactions to finish. Bind generations to running writer versions so a stale invocation cannot adopt the newly opened generation. Bound waits and reject new work promptly while closing. Inventory autocommit SQL, auth/session and operator writes, scheduled purge, extension and routine claims/completions, usage callbacks and privileged functions. Account separately for jobs and external effects that outlive their transactions. Give admitted work a bounded way to finish, or reconcile its durable outcome before DDL.

Roll out support under the existing timed drain first. Enable early completion only when all deployed writers for the affected scope support the protocol, their admission is closed, and all conflicting in-flight work and leases have settled. Retain the timed path for legacy writers. An uncertain lease, failed ownership check or lost migration lock must keep DDL gated. A replacement migration process must reacquire ownership and reconcile the journal before proceeding.

**Acceptance.** On real Postgres race admission against close, kill a pooled connection mid-operation, retry an old invocation after reopen, and interrupt the deployer on either side of DDL commit. Exercise a delayed extension callback and a routine awaiting a tool. Assert zero stale commits, cross-workspace writes or duplicate external effects. With no active writers or leases, target **under 10 seconds from admission closure to permission to migrate** in staging. Report DDL, code updates, and route restoration separately. Test old-product/new-deployer and new-product/old-deployer combinations before enabling fast completion.

## Task 3 — Keep compatible reads and unaffected operations available

**Verified in staging and production.** Dedicated readers serve existing sessions and supported web, REST, and MCP reads during a write pause for a reviewed migration that adds eligible plain, non-unique B-tree indexes. All 110 staging read samples passed during the pause. Writer admission still closes globally, so workspace- and extension-scoped upgrades use full maintenance. [Retainer #170](https://github.com/Tamloot-cc/Retainer/pull/170) · [Retainer #177](https://github.com/Tamloot-cc/Retainer/pull/177) · [Cloud #37](https://github.com/Tamloot-cc/retainer-cloud/pull/37) · [Restricted serving runbook](https://github.com/Tamloot-cc/retainer-cloud/blob/a62bef3/docs/restricted-serving.md)

The production release added the extension-job connection index. For each of REST, MCP and signed-in account reads, 243 first attempts succeeded across the rollout, including 133 in the recorded restricted interval. The People list rendered from an existing browser session while the reader served traffic. All 136 refused synthetic writes carried the guaranteed-unexecuted marker and a five-second retry hint. Their first-to-last span was 4 min 32 sec. All 106 successful synthetic writes passed read-back, and the routine canary succeeded after 5 min 18 sec. [Index change](https://github.com/Tamloot-cc/Retainer/pull/184) · [Production release](https://github.com/Tamloot-cc/retainer-cloud/actions/runs/45447065582)

With an exclusive workspace schema lock held on real Postgres, the restricted reader served session metadata, record queries and pinned MCP reads for the target workspace. It rejected REST and MCP mutations before execution. A second workspace read and wrote over both protocols, and its record stayed outside the first workspace's results. An isolated AWS staging fixture repeated these checks through API Gateway with temporary handlers and two synthetic workspaces. This exercise covered HTTP request routing and database isolation. Hosted writer admission continues to operate globally.

**Deliverable.** Add a restricted serving mode with an explicit list of supported operations. Start with opening the web app in an existing session, listing and viewing records, search, and equivalent MCP reads. Classify the operation after decoding the request, including POST searches and MCP tool calls. Inspect its whole path through authentication, session refresh, rate limits, authorization, and database access. Preserve tenant isolation, credential revocation and existing access checks. Enforce read-only database transactions for the supported read path. If a required side effect or permission check cannot be performed safely, return temporary unavailability for that operation.

The deploy plan must establish that the serving version can read every intermediate schema and that the migration's locks permit those reads. Keep the verified handlers and their assets serving during the write pause. A release can restrict only extensions, or one workspace for a workspace-local upgrade, once its shared dependencies and every entry point into that scope are covered. Use full maintenance for global permission transitions, blocking table rewrites, or any case with uncertain isolation. Keep queued background delays visible independently.

Refused operations use the existing maintenance response and Retry-After. Emit the guaranteed-unexecuted header only when rejection precedes every side effect. Keep unsaved edits mounted and show which operations are paused. Restore each scope after its compatibility and health checks pass. [SDK retry contract](../../packages/sdk/src/maintenance.ts) · [Web retry handling](../../packages/web/src/api/maintenance.tsx)

**Acceptance.** During a write pause, exercise authenticated web, REST, and MCP reads continuously with zero deployment-induced failures on the declared read set. Test expired/revoked credentials and cross-tenant access. Race a mutation with closing admission and verify either one committed result or an accurate retry response. Verify an unsaved edit survives recovery. For a workspace-scoped fixture, a second workspace must keep reading and writing. For a shared-table lock fixture, the plan must select full maintenance before starting the blocking operation.

The hosted ops command `backfill-search-text` repairs stale search vectors one
workspace at a time. Pass `protocol: 1`, the `workspaceId`, and an optional
`batch` of up to 100 records. Run it from the admitted serving build after the
journal is current. Each invocation commits one batch. The result reports
`rebuilt` and `pending`. Retry with a delay when `pending` is true, including
when skipped row locks leave an empty batch. The normal record write path
continues maintaining vectors throughout. The stopped migration path handles
incompatible search changes. [Retainer #185](https://github.com/Tamloot-cc/Retainer/pull/185)
