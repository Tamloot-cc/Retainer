API introduction / From evidence to typed answers

One shared input.
Independent questions.
Typed answers.

Send evidence to POST https://api.openai.com/v1/decisions. Luna evaluates each question against that same evidence and returns the answer shape you requested. Your application validates the result and chooses the action.

answers[]

Find the matching name

Each answer echoes its question name. A choice returns a label, probabilities over options and a separate confidence value. A predicate returns one probability. A score returns an expected level index.

usage

Account for input

Input usage includes cache reads/writes. Those detail counters are part of the total, not extra tokens to add again. Questions also consume input tokens.

application policy

Validate, then decide

A label is not merge permission. Refusal, invalid data and incomplete context defer the pair. Probabilities and confidence are model estimates, not measured accuracy.

Supported inputs, limits and explanations
Shared inputText or ordered messages, including supplied tool calls and matching outputs. User-message content can include text, images and JSON. CRM URL strings are evidence; they do not trigger website browsing.
Question typeschoice selects from allowed values; predicate estimates a condition’s probability; score returns a probability-weighted index over ordered levels.
FallbacksUse an insufficient-evidence choice where appropriate. A provider refusal is a separate typed answer; other questions in the request can still receive answers. Treat request errors separately too.
Context lengthLuna’s model page lists 922,000 maximum input tokens and a 1,050,000-token context window. An endpoint-specific Decisions ceiling was not verified in the spike. Our pair-context budgets are deliberately much smaller.
ExplanationsDecisions returns typed judgments rather than generated prose. An evidence-reference choice can select a supplied source ID or none; the application validates that reference and renders a fixed explanation template.

Product decision
Try a human-reviewed pilot in one workspace.
Round 10 failed its predefined zero-error gate. We subsequently reconsidered that requirement for a queue where a person accepts or dismisses every suggestion. The owner’s workspace is the proposed opt-in pilot. Its real review workload and accuracy are still unknown.

What the reviewer sees
Show both records side by side with the exact source excerpt, its provenance and the names it refers to. Label the pair as a possible duplicate. A human approves each merge.
What the pilot should measure
Keep the 0.50 source cutoff frozen. Compare review time and queue size with the existing matcher. Track accepted and dismissed pairs, flag misleading excerpts, and sample withheld pairs for genuine duplicates.
