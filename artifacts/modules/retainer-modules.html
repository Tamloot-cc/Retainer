Modules

A module is a feature we build inside Retainer's server, kept in its own folders, so each workspace can switch it on or off, and we can delete it cleanly if the experiment fails.

Parked on 2026-11-27. No module is planned. Dashboards, which was going to be the first module, is a core feature like views and Routines (section 5). The design waits here for the first real experiment.

2 · Four places a feature can live

Always start with the cheapest place that works

1 · cheapest

Configuration

Fields, views, templates and Routines. A workspace sets it up, no release.

Pick it when the data model and a rule are enough.

Tags, lead scoring, "when a deal moves, create a task".

2

Extension

A sandboxed function. Brings data in from other services, or uses a model to work on it.

Pick it when the feature talks to the outside world or needs AI.

Gmail, Granola, enrichment, transcription.

3

Module

Code inside the server, with its own tables, API routes, agent tools and screens.

Pick it when the feature needs new screens or its own data inside Retainer.

Goals, reminders on records, CSV import. None is planned.

4 · most expensive

Standalone app

A separate product with its own database, that also serves people who aren't members.

Pick it when guests use it, or it has its own hard rules.

Booking, client portals, intake forms.

One rule keeps modules small: what it learns goes in records

Knowledge goes in records core

What a module learns about a person, a company or a meeting is written as records, events and facts, through the core write path.

searchget_contextmergeforgetchange feedRoutines

All of these work with no module code, and the knowledge stays if the module is removed.

Feature state goes in module tables module

A module's own tables hold display settings, job state and pointers. Nothing else.

display settingsjob statepointers

Example, Recording: audio goes with the core's files, the transcript becomes the event's full text, and the module's table only says which upload belongs to which event.

6 · Example: Recording

Does "record a meeting and save it as an event with notes" fit?

Partly. Recording does three different jobs, and each one belongs in a different place.

Module

1. Record

  • A record button and recorder screen in the web app
  • Upload the audio to Retainer's file storage
  • Create the meeting event and attach the audio

New screens inside Retainer, so only a module can do it.

→
Extension

2. Transcribe and write notes

  • The new event starts it
  • Sends the audio to a speech-to-text service
  • Asks a model for notes, through the model proxy

Outside services and a model, so a module may not do it.

→
Core

3. Keep it

  • The transcript is the event's full text
  • Notes and facts are written on the event and the people
  • Search, the agent and forget work on it as usual

Knowledge goes in records, so nothing new is needed here.

If Retainer records the call itself

You need a small module (the recorder screen and the link between upload and event) plus a transcription extension. The module is thin: it holds almost no data, because everything it learns is on the event.

If something else records the call

A meeting bot, Tamloot or Granola already records it. Then you need no module at all. One extension brings in the meeting as an event with its transcript and notes, the way Granola does today.

So the simplest test is the cheapest one first: try Recording as an extension on top of an existing recorder. Build the module only if people need to press record inside Retainer.

Up to three folders, all named after the module. Delete them and the feature is gone.

9 · Who may import what

Modules sit between the core and the interfaces

Three import rules

  • A module may use everything below it: records, schema, search.
  • A module never imports another module. Two that need each other are one module.
  • The core never imports a module. Only the list in modules/index.ts does.
10 · On and off

A module is on only when all three say yes

Settings → Experiments

Dashboards Live dashboards the agent writes and people pin.

Lists the modules the instance offers, each with its description and a switch. A workspace admin flips it. An illustration, not the final screen.

When it's switched off

  • Screens, sidebar item and tools disappear at once, even in chats already open.
  • Its data waits untouched. Switch it back on and everything is there.
  • Admins switch one module at a time, so two admins never undo each other.
11 · Keep or delete

Try it, then keep it or delete it

Deleting a module deletes its tables in every workspace. So switch it off first, and delete it in a later release. Records and events it wrote stay.
