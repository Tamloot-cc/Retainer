1 · The idea
ConceptSystemDataRulesCode

Memory for agents that work with CRM data

Agents read conversations with their own model and decide what to keep. Retainer validates it, resolves conflicts, keeps its history and makes it searchable. It never calls a model itself.

Idea 1 · from Twenty

Schema as data

Objects, fields and relations are rows, so a workspace, or an agent in it, can extend the CRM at runtime with no DDL.

Idea 2 · after Honcho

Memory with provenance

Every value records who wrote it and which event it came from. Values are claims; the current value is computed from them.

Rule · no model in the core

Deterministic

Writes, conflicts, search and consolidation never call a language model. Only extensions may, through the model proxy.

3 · Data model
ConceptSystemDataRulesCode

Three layers in one database

Metadata describes the shape. Records hold the current values. Memory holds the claims and evidence the values come from. Record values are a cache: they can always be rebuilt from the claims.

Schema (metadata)The shape of the CRM, as rows
object_typesfieldsschema_changesviews
RecordsCurrent state, derived
records.data (jsonb)record_linksrecord_identifierscomments
MemoryClaims and evidence, kept forever
field_assertionsfactsfact_sourcesevent_recordsevent_linksevent_movesevent_identity_tombstones

The highlighted claim wins: a person's value outranks newer agent claims (section 5).

Why JSONB and not a table per object

  • An agent adds a field as one metadata row: no DDL, locks or partial failures
  • One fixed schema with normal migrations for self-hosters
  • Many hosted workspaces without bloating the Postgres catalog

What real tables would give is kept another way: foreign keys on record_links, uniqueness through record_identifiers, and a shared GIN index for filters.

Field types

textnumberbooleandatedate_timejsonselectmulti_selectmoneyemailsphoneslinksfull_nameaddressrelationfiles

Composite shapes (money, emails, address…) are defined once in @retainer/shared. Relations live in record_links, not in data. File bytes stay in external storage; only immutable file IDs are stored.

4 · A write, end to end
ConceptSystemDataRulesCode

After a meeting, an agent makes four calls

Each call is its own short transaction, so an agent that stops halfway leaves consistent data and can resume. Retainer never creates records on its own.

  1. 1 · log_event

    Log the event

    Type, channel, external ID, time, title, summary, participants (emails, phones or IDs), about records.

  2. 2 · upsert_record

    Update records

    Cite the event as source, so values carry its date and an older email can't overwrite a newer claim.

  3. 3 · remember

    Store facts

    Plain-language facts citing the same event, with an optional quote.

  4. 4 · upsert_record

    Create tasks

    Commitments someone made, as task records.

Privacy lock first, then schema (lockForWrite in db/tx.ts), the same order extension imports use.

HandleDana@Acme.com
→
Normalizelowercase email, E.164 phone
→
Match a unique identifierrecord_identifiers
→
matchedlinked to the person
or
unmatchedno_match · phone_only · ambiguous · deleted_record · suppressed

The agent creates the people worth keeping, then logs the same event again with the new record ID. A retry with the same (channel, externalId) returns the same event and only adds links.

5 · Write rules
ConceptSystemDataRulesCode

Who wins a field

First by who wrote it, then by when it was true at the source. The server sets that time: the cited event's time, or the write time.

usera person
>
integrationa sync or standalone app
>
agentan AI agent's key
>
systemseeds, templates

Ties at the same rank: latest observed_at, then created_at, then assertion ID. The actor always comes from the credential, never the payload.

Accepting a pending claim re-asserts it as the reviewing person, keeping its source and time. Agents never silently overwrite people, and are never silently ignored.

Rule 1

Actor and source

Every write has an actor. Every fact cites an event; without one, remember logs a hidden internal note to cite.

Rule 4

Always recomputable

Pending and rejected claims never count. Deleting an event retracts what cites it and recomputes the fields it was winning.

Rule 5

Serialized per record

A row lock around insert + recompute, so two agents never lose each other's values. Deadlocks retry up to three times.

6 · Events
ConceptSystemDataRulesCode

Things that happened are records too

An object type is an entity (it has state people change) or an event (it happened and is cited as evidence). Only log_event creates events. The base type is conversation, with a medium: meeting, call, email, message.

A hosted workspace created without a template starts from scratch, with only the hidden types; its first agent designs the rest.

Every list of a record's events says via how it got there. An event appears once: direct beats rollup.

Object or event?

  • Object: a task, deal or ticket. Its changes are its history, never events.
  • Event: a call, payment or form submission, from a source, cited as evidence.
  • Comment: a person's remark on any record. Never evidence; only people write them.

Hidden built-in types

  • Internal note: what remember cites when no event is given.
  • Workspace profile (workspace): how the business works.
  • Member profile (me): private to one person, enforced by RLS.
7 · Schema engine
ConceptSystemDataRulesCode

One entry point for every schema change

Seeds, upgrades, templates, people and agents all go through the same pipeline, under the workspace's exclusive schema lock.

  1. 1

    Load

    Current schema, exclusive lock.

  2. 2

    Apply

    Operations in memory.

  3. 3

    Validate

    Names, reserved words, targets, options.

  4. 4

    Diff

    Current vs desired → operations.

  5. 5

    Classify

    Additive or destructive.

  6. 6

    Apply or propose

    schema_version + 1.

ChangeBy a person with adminBy anyone else, including an agent with an admin key
Additive: new object, optional field, new option, labelAppliedApplied
Destructive: rename, delete, required or unique, remove optionApplied: the request is the approvalStored as proposed until a person approves
Change a field's typeNot supported: create a new field instead

Protected elements

Server code finds what it depends on by universal ID: person, company, task, task.status (its done option), task.dueDate, every event type's title and summary, and the internal-note type. They can be renamed, never deleted or reshaped.

Templates

salesservicesclinicreal_estaterecruitingblank

Additive only, so applying one needs no approval. Upgrades add what a workspace never had, matched by universal ID, and never re-create what it deleted.

8 · Reads
ConceptSystemDataRulesCode

Six ways to read, all assembled by rules

No read is summarized by a model: summarizing is the agent's job. There is no ask endpoint.

describe_schema

Objects, fields, built-ins, value formats, whether the workspace is initialized.

query_records

Filter, sort, page one object; event for every event type at once.

get_record

One record with links; an event with participants and about; newest comments.

search

Keywords across records, events and facts. Postgres full-text only.

get_context

A pack fitted to a token budget: fields, linked records, facts, recent events.

get_timeline

How a record got here: events, field changes and facts, newest first.

No embeddings and no BM25: plain Postgres with pg_trgm, btree_gin and unaccent. Every index leads with workspace_id.

About four characters per token; default 2,000, at most 16,000. Items are never cut mid-text, and omitted counts what didn't fit.

9 · Deletion and privacy
ConceptSystemDataRulesCode

Soft delete by default, forget for privacy

Deleting hides a record and retracts what its events supported. forget erases a person for real, and only a person with admin can run it.

  1. 1

    Suppress

    Emails and phones as keyed HMACs, so they can't come back.

  2. 2

    Erase events

    Events they took part in, with what rested only on them. Tombstone the identity.

  3. 3

    Fix the rest

    Remove inbound relations and recompute surviving records.

  4. 4

    Hard delete

    Record, claims, facts, links, identifiers, comments, stored responses.

  5. 5

    Audit

    Actor, time and counts only. No names or values.

What makes it safe

  • A workspace privacy lock: writes take it shared, forget exclusively
  • The HMAC key lives outside the database (RETAINER_SUPPRESSION_KEY)
  • Routines: stored tool and model results are cleared, and queued or running runs end as erased
  • Candidates for human review: other records mentioning the name

What it does not promise

  • Finding every fact that mentions the person on another record
  • Redacting only one person from a shared meeting: the whole event goes
  • Backups: the operator's responsibility
10 · Background work
ConceptSystemDataRulesCode

The consolidator and the job queue

The queue is Postgres itself. Every minute a worker asks which workspaces are due and runs each under a per-workspace try-lock, so two workers never run the same one.

The consolidator does

  • Supersede exact duplicate facts (same record, text and validity)
  • Suggest merges: shared email, phone or URL, or labels with trigram similarity ≥ 0.6
  • At most 500 new suggestions per kind per run

It never

  • Merges records: a person does, with POST /v1/records/:id/merge
  • Supersedes near-duplicates or contradictions
  • Calls a model or flags stale values

Workers also run the extension and routine executors, change dispatch and file maintenance. Routine code runs in the same closed sandbox, with a run token of agent rank (ARCHITECTURE.md 4.7).

11 · Tenancy and auth
ConceptSystemDataRulesCode

Every credential becomes one Caller in one workspace

The workspace is the security boundary. The application checks access, and Postgres row-level security checks it again on every query.

Key mode (default)

An operator creates workspaces and keys with the CLI. Self-hosted starts with one workspace and an admin key printed on first boot. The web app signs in with a key, kept in an HTTP-only cookie.

Accounts mode

Better Auth in-process: Google, Microsoft or a passkey, no passwords. Organizations, invitations, roles, MCP OAuth for Claude's web app. Roles are bundles of scopes.

viewer = readeditor = read, writeadmin = all four

Human-only actions check the actor, not the scope: forget, destructive schema changes, merges, accepting review items and moving events all need a user. An agent with an admin key still can't do them.
