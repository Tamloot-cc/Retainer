1 · The big picture

Three pieces. Only one holds the tools.

All tools live on the server, at /mcp. The bridge and the plugin only carry connections to it, so a new tool reaches every agent without a client update.

2 · One request

Every call builds a fresh server for one caller

There are no MCP sessions. Each HTTP request is authenticated on its own, and the workspace and actor come from the credential, so no tool takes either as input.

requestPOST /mcpBearer API key or OAuth token
→
middlewareauthenticatesame as REST · yields the caller: workspace, actor, scopes
→
middlewarerate limitper workspace, counted in Postgres
→
createMcpServertools for this callerroutine tools only if routines are on
→
run()scope check, then serviceerrors mapped exactly like REST

What a tool returns

// success: JSON as text and as structuredContent
{ "content": [{ "type": "text", "text": "{…}" }],
  "structuredContent": { … } }

// failure: the same body REST returns
{ "isError": true,
  "structuredContent": { "error": {
      "code": "invalid_request",
      "message": "what was wrong, what is allowed",
      "details": { … } } } }

The server instructions end with "read the message and retry", so error text is written for agents to act on.

Deliberate choices

  • Stateless. Fits Lambda: nothing to keep between requests.
  • No list-change notifications. The tool and prompt lists are fixed, and a listen stream would stay open until Lambda times out (#47).
  • Generic tools. One upsert_record for every object, so a workspace's custom objects never change the tool list.
  • Run tokens are refused. An extension run uses REST only, so it can't reach tools beyond its function's needs.
  • The key stops at the middleware. Tools get the caller, never the token.

The four guides

discover_schema

Explore the user's own data, propose a schema with evidence, apply it once they agree. Prompt takes an optional sources.

schema_design

Start lean; prefer events, facts and tasks over new objects; grow fields from evidence. Also how to review a schema.

memory

What goes in workspace (how the business works) vs me (the person), and what belongs on a record.

log_from_chat

What a chat holds that is worth keeping, which source to cite, and the order of writes. The hook points Claude here.

4 · Connecting

Two credentials reach /mcp

An API key, made by an admin for one agent, or an OAuth token, which a person grants by signing in. OAuth needs accounts mode, which the hosted service runs.

OAuth sign-in, as the plugin and Claude web do it

One connection = one workspace. To use another, connect again and pick it. Disconnecting, removing the person or lowering their role applies on the next request.

An agent that only has the URL

An anonymous GET /mcp returns plain-text setup steps (a browser is redirected to /mcp/setup). They cover Codex and Claude Code, re-auth and workspace checks. Every /mcp response also carries a Link: rel="help" header to them.

The stdio bridge

"retainer": {
  "command": "npx",
  "args": ["-y", "@retainer/mcp"],
  "env": {
    "RETAINER_URL": "https://retainer.example",
    "RETAINER_API_KEY": "rtn_…" } }

Diagnostics go to stderr only. A rejected key fails with a message naming RETAINER_API_KEY.

5 · How agents write

The server instructions teach one routine

Retainer never reads conversations. The agent does, then writes in a fixed order so every value can cite where it came from.

At the start of a session

describe_schemaobjects, fields, value formats, initialized
→
Not initialized?follow discover_schema, apply only after the user agrees
→
get_context("workspace")shared memory: how the business works
→
get_context("me")if the credential works for a person

After a meeting, call, email thread or chat

step 1log_eventtype, channel, time, title, summary, externalId, participants, about. Keep the id.
→
step 2upsert_recordsource = that event, so an older email can't overwrite a newer value
→
step 3rememberfacts that don't fit a field, citing the same event
→
step 4upsert_record taskfor what someone committed to

Each call is its own short write, so an agent can stop and resume. Logging the same channel + externalId again returns the same event and only adds missing participants and about records.

What a write can come back as

applied

It is now the value.

pending_review

A person set a different value. Yours waits for their approval, so the agent must say "waiting", not "done".

superseded

Kept in history. A newer or higher-precedence value stands.

Guardrails built into the tools

  • upsert_record finds by id or a unique match, and fails if nothing matches unless ifMissing: "create". "Update Dana's address" can't make a second Dana.
  • Unmatched participants come back with a reason. Retainer never creates records on its own.
  • Adding fields applies at once. Renames and removals wait for a person.
  • Validation errors name the field and the expected format.

What agents can't do

  • Write comments. Those are people talking to people (403).
  • Cite a comment as a source.
  • Run move_events for real. Agents pass dryRun: true; an admin person runs it.
  • Delete a fact, or supersede one a person wrote.
  • Put customer knowledge in me.

7 · The CRM check hook

After each turn: filter, ask Haiku, maybe wake Claude

The check runs in the background, so you never wait for it. A cheap model makes a yes/no call; only on yes does Claude wake, read the guide and decide what, if anything, to log.

Runs on your machine, in the background Model call, under your Claude account Retainer, reached only by Claude's own tool calls

The skip filters, in order

  1. 1RETAINER_CRM_HOOK=offexit
  2. 2Claude was just woken by this hookskip
  3. 3This turn was already checkedskip
  4. 4A task or the hook started it, not a personskip
  5. 5A slash commandskip
  6. 6The turn already used a Retainer toolskip
  7. 7Under 200 characters, with the turn beforeskip
  8. →Ask Haikuclassify

The classifier call

Runs
claude -p --safe-mode --model haiku: no CLAUDE.md, hooks, plugins, MCP or skills
Tools
None (--tools "")
Input
The turn in <turn> (≤ 12,000 chars, trimmed in the middle) and the end of the turn before in <previous_turn> (≤ 3,000)
Output
{"log": bool, "what": "one line"}, enforced with --json-schema
Timeout
90 s, then killed

What Haiku is told

  • A conversation had or scheduled with someone named
  • Someone's contact details, role, organization or needs
  • A tracked thing that started, changed, stalled or ended
  • A promise or follow-up between the person and someone else
  • An email, event, note or transcript Claude read about someone
  • The person's own engineering work: code, deploys, CI, tools
  • Talk about the CRM itself and its data model
  • How-things-work questions or public research
  • A lookup that found nothing

Why it's built this way

Leans to yes
Needless wakeClaude says "nothing to log" in one line
Missed turnThe information is gone

When unsure, Haiku answers yes. Claude is the careful second look.

Static wake message

Haiku's what line goes to the log only. Claude gets fixed text plus safe IDs, so a turn that quotes a customer's email can't steer it. The turn's tags are also broken (<turn_) so chat text can't close its own frame.

No model in Retainer

The classifier runs on your machine, under your Claude sign-in, and sends nothing to Retainer. Retainer's core still never calls a model.

You may have moved on

The wake names which turn to reread ("the turn you started 2 messages before your latest one") and ends with "Do not resume any earlier task."

When something goes wrong

SituationWhat Claude tells youHow often
Node.js not foundInstall Node 20+, or set RETAINER_CRM_HOOK=offOnce, ever
claude -p sign-in expiredRun claude auth loginOnce a day
3 failures in a row, any other reasonWhere crm-check.log is, and the off switchOnce a day
Woken, but Retainer tools missingRun /mcp and sign in, or turn the check offEach wake
Any other errorNothing. Logged, exit 0Never shown

State lives in ~/.claude/plugins/data/<plugin>/: crm-check.log has every decision and why; state.json holds the last checked turn per session (last 200 sessions) and the failure counters. Several sessions write it at once, so each update re-reads the file first.
