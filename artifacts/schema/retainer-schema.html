Retainer · schema design

Retainer schema: today and proposed

Today every workspace is expected to have four built-in objects, and Retainer's own features and every extension find them by fixed IDs. The accepted design removes them: the workspace's schema is its own, core features read generic marks, and each extension gets an approved plan of where its data goes.

1 · Big picture

Who decides the schema

Today, Retainer assumes four objects exist. In the proposal, the agent designs the schema, and Retainer and its extensions adapt to it.

Retainer core Extension The workspace's own schema Approved installation plan Built-in, found by fixed ID
Today
  • Four built-ins with fixed IDs, protected in every seeded workspace
  • Hosted workspaces start "from scratch" without them
  • Core features and every extension look them up by ID
  • Templates add to the built-ins, and upgrades keep them in sync
Proposed
  • No built-ins. The four become a starter template
  • Core reads one generic mark: closed on select options
  • Extensions name nothing; each installation holds a plan
  • A person approves every plan. A model may propose one

  2. 2 · section 5

4 · Layer: workspaces and templates

A template is a one-time copy onto an empty workspace

After that, the schema belongs to the workspace. Releases never change it, and templates become designs an agent can borrow from.

A template on a workspace that already has any visible type is refused with workspace_not_empty, so name clashes and partial applies can't happen.

5 · Layer: closed options and open items

One mark replaces the Task object as far as core is concerned

Open tasks needed to know which object holds tasks and which status means done. A closed mark on select options answers the second question for any object, which makes the first one unnecessary.

Rules

  • Any select field on an entity object. Not multi-select
  • Marking follows the approval rule for relabeling an option
  • The guide: mark only work items (tasks, deals, applications), not lifecycle tags on people or companies
  • Templates ship with their end states marked
  • An empty value counts as open

6 · Layer: extension bindings

Extensions speak their own words. The installation translates.

An extension declares bindings: "meetings", "tasks", "people", with the fields and values it produces. Each installation stores where every binding goes in this workspace.

The names on the right are whatever the workspace chose. Tamloot never sees them in its manifest; it learns them at run time from the plan.

For each binding, the admin picks one

Existing

Use an object you have

Same class (entity or event). Hidden types, inverse relations, read-only and event core fields can't be bound.

Create

Make the suggested one

An ordinary workspace object, which you can reshape later. If the name is taken: tamlootBooking, "Bookings (Tamloot)".

Skip

Leave it out

Optional bindings only. Whatever uses it stays off, for example Tamloot's tasks.

owned: structure only the extension defines

Always created by the extension, as an installation contribution, never bound to something you already have. It says nothing about who may write values.

  • Booking's booking object
  • Last contact's lastContact fields, which a person can still correct

How the six extensions declare it

  • Tamloot: meeting, task (optional), person
  • Granola: meeting (url, medium, transcript), person
  • Gmail: email (medium = email), person, match only
  • Enrichment: company, domain as lookup, outputs as fields
  • Last contact: contact (read, any number of event types), person and company
  • Booking: owned booking object, person as a read-only relation target
7 · Layer: the install review

Someone proposes, a person approves

The model can suggest a plan. It never decides one. Approval commits the plan, the schema changes it needs, the grants and the triggers in one transaction.

1 · configure runthe extension's own code, may call the model, gives a reason per choice
or
2 · your agentthrough preview_extension, shown as an agent proposal
or
3 · fixed defaultan object with a matching name and fitting fields, else create, else skip
→
Admin reviews and approvesedits any choice first

Four checks in the review

Match field unique

When the plan creates people, the emails field must be unique. The review can include making it unique.

fixable in review
Required fields covered

Every required field of an object the extension creates records in must be one it fills. The review can make others optional.

fixable in review
No shared destinations

Two outputs can't write one field, and nothing writes the lookup field.

refused
Closed matches both ways

done needs a closed option, open an open one. An install never changes an existing option's mark.

refused

The review never shows "the schema change is invalid" alone. Each problem is in plain words, next to the binding it concerns.

8 · Layer: the plan over time

One plan, guarded while active, changed only by a re-plan

This was the hardest part to get right: it took five review rounds. The final rule has four parts.

Red: while the plan is active, a schema change that would fail the install's own checks is refused, naming the extension.

1 · Holds
While installed, the schema engine refuses any change after which the install's checks would fail: deleting a bound field, un-marking a bound closed option, dropping uniqueness on a match field, adding a required field it can't fill.
2 · Re-plan
The only way to change the plan. It stops old runs, applies the new plan's schema, re-runs setup and re-verifies connections, and keeps pending change work.
3 · History stays
A re-plan never moves imported data (below).
4 · Uninstall
Releases everything. A reinstall proposes surviving destinations again and creates replacements for deleted owned parts.

Rule 3: re-planning Tamloot's meetings from meeting to call

  • Tasks: if any task destination changes, synced tasks are detached inside the re-plan, keeping their values. They're never moved or recreated.
  • A moved lastContact retracts the extension's old claims and keeps people's.
  • A field the plan stops using goes back to the workspace, which can delete it.
  • Relations and views keep their original targets.

Reads by name, managed writes by key, standalone writes by ID

Source eventsGo to the plan's event object. A receipt stores the projection it was accepted under, so a same-revision replay compares only within it.
Source tasksIdentity stays per source account in source_tasks; no ID field on your object. One lock per installation; the same task ID from another account fails closed.

10 · Delivery

Two PRs. The first stands alone.

PR 1 · closed options and open items
  • The closed mark, on today's schema
  • End states marked in the base definitions and every template
  • Migration: existing workspaces get the marks, so done tasks never show as open
  • Open-items read, get_context, the Open tab, guide text
PR 2 · no built-ins and bindings
  • No seed, starter, one-time templates, protection cleared
  • Shared constants and baseObject removed with their last users
  • Bindings, the plan, the bindings endpoint, install review, re-plans
  • All six extensions moved over; existing installations bound by migration
  • Rebuilt bundles and the hosted release steps
11 · How it was reviewed

Five rounds, two reviewers, one lead

Claude Code and Codex reviewed independently each round. The lead ruled on every issue and revised the spec. Rounds 4 and 5 were limited to the plan's lifecycle.

RoundWhat changed
1Owned parts, bindings for reads, one PR that builds, templates only on empty workspaces, closed marks both ways
2Templates become one-time copies; pinned versus editable bindings; bounded open items; per-installation task lock
3Pinned bindings follow the contribution rule; editable changes re-run setup
4The pinned/editable split goes: one plan, guarded by the install's own checks, changed only by a re-plan; history stays
5Reviewers accept the plan. Six one-line fixes: createPeople in the plan, released fields, task detachment, pending work, stable field IDs

Out of scope by decision: due-date ordering of open items, writing one binding to several objects, and moving a source's imported history to another object.
